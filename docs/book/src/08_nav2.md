# Nav2: making a 0.42 m robot fit a 1.3 m door

## 8.1 Four parameter files, four jobs

The project keeps navigation parameters physically separated by *role*, not by convenience:

| File | Used by | Velocity | Purpose |
|---|---|---|---|
| `config/nav2_params.yaml` | mapping runs | `max_vel_x 0.15` | slow, safe mapping |
| `config/nav2_params_nav.yaml` | acceptance / agent runs | `max_vel_x 0.26`, `min_vel_x −0.15` | faster; the file behind every number in this book |
| `config/nav2_params_explore.yaml` | exploration | as above | exploration-specific planner and BT |
| `config/nav2_params_explore_navfn.yaml` | experiment arm | — | control arm copy (identical except comments) |

The rule: **experiments may only modify the `*_explore*` files and `nav_to_pose_explore.xml`.**
The two acceptance files are frozen. This is what makes "the acceptance still passes" a
meaningful statement three phases later.

## 8.2 The numbers that decide feasibility

```
robot_radius            0.23 m     (circumscribed footprint ≈ 0.21 m + margin)
inflation_radius        0.45 m
cost_scaling_factor     3.0
door width              1.30 m
corridor clear width    2.88 m
goal tolerance (xy)     0.20 m
progress checker        0.25 m within 6.0 s   (exploration: 0.25 / 6.0)
```

Two consequences worth internalising before touching anything:

**(a) The door is not the problem.** A dwell-time-free geometric check of every door's widest
path gave half-widths of 0.50–0.55 m, all ≥ `inflation_radius` 0.45, i.e. cost **0** at the
narrowest point. "The robot cannot get into the study because the door is too narrow" was
falsifiable in 20 minutes of computation, and false.

**(b) The goal point can be the problem.** The same probe applied to *failed* goals found their
own clearance to be 0.35–0.40 m — just inside the inflation radius. Inside that band the cost
field is non-zero (132–177 units per cell in the observed cases), and DWB must traverse the
entire band to reach the goal. It frequently prefers to rotate in place instead. That is the
mechanism behind most "the robot reaches the door and then spins forever" failures, and it is a
*goal placement* bug, not a planner bug.

## 8.3 Where the costmap comes from

```yaml
local_costmap:
  plugins: ["voxel_layer", "inflation_layer"]
  voxel_layer:
    observation_sources: scan
    scan: { topic: /scan, data_type: "LaserScan", max_obstacle_height: 2.0,
            raytrace_max_range: 5.0, obstacle_max_range: 4.0 }
```

Note what is *not* there: no point cloud source, no camera. Four parameter files, all with
`observation_sources: scan` and `data_type: "LaserScan"`. The `VoxelLayer` is used as a 3D
*container* for a 2D input — it does not make the obstacle layer three-dimensional.

Consequence: everything the projection slice cannot see is invisible to navigation, including
furniture overhangs, table tops and anything above 0.85 m in the 2D world because it was raised
there deliberately.

## 8.4 Why the controller "decides" to stand still

The single most useful debugging artefact in this project is the trajectory evaluation dump.
In a stall, all 419 candidate trajectories were *valid* — and the chosen one had `vx = 0.000`
with a score of 63.40, beating a `vx = 0.103` trajectory that scored 72.70. The slower
trajectory won because the faster one had to cross `BaseObstacle` cells with `raw = 195`
(i.e. ~0.30 m from an obstacle).

So the robot was not stuck, confused, or blind. It was **optimising correctly against a cost
function that made standing still rational**. This is why the project's first question about
any stall is "which critic dominates?" and not "is the controller broken?".

Two corollaries:

* "No valid trajectories = 0" is *not* a health metric. A healthy-looking zero coexists with
  a completely motionless robot.
* Tuning the stall *timer* treats nothing. It was tried: an 18 s watchdog produced no
  improvement (4 vs 2 stalls, worse coverage 56.5 vs 45.0 m²), so the 12 s setting was kept and
  the effort moved to goal reachability.

## 8.5 Behaviour tree

Two trees exist. The acceptance tree is stock `navigate_to_pose_w_replanning_and_recovery`.
The exploration tree (`config/nav_to_pose_explore.xml`, 48 lines) changes the recovery
structure — notably a BackUp-first branch, which was A/B tested: it survives more stalls
(stalls 2 vs 4) but is 44 % slower and covers less area (37.6 vs 45.0 m²). It was *not*
adopted; the measurement is kept because the question ("would recovery behaviour help?") will
be asked again.

## 8.6 Progress checker, and what it really measures

A 0.25 m / 6 s threshold sounds generous; against a 0.15 m/s mapping speed it is ~1.5 m of
expected travel. In practice the checker fires during *legitimate* slow manoeuvres (turning in
a doorway at 0.1 m/s with 0.3 m/s² acceleration). The lesson recorded in the project notes:
the progress checker detects "no displacement", not "no progress"; a robot rotating to align
with a door is making progress while failing the checker. Exploration therefore treats a
progress-checker stop as a *candidate* stall, filtered by the observed rotation rate.

> **Takeaways.** Four parameter files, one freeze rule. Doors are innocent; goal clearance is
> guilty. The costmap sees exactly one horizontal slice. The controller stalls because
> standing still is cheaper — read the critics, not the symptoms. Recovery experiments are
> measured and, so far, rejected.
