# The semantic map: a database, not a perception system

## 11.1 What it is

`config/semantics.json` (11 KB) contains eight room records (seven rooms plus the corridor) and
61 object records in 33 classes:

```json
{ "id": "fridge_1", "class": "fridge", "room": "kitchen",
  "x": -2.66, "y": 5.20, "yaw": 1.571, "w": 0.78, "d": 0.78 }

{ "name": "living_room", "label_zh": "客厅",
  "rect": [-8.89, 1.56, -3.20, 6.89], "center": [-6.045, 4.225],
  "door_center": [-6.0, 1.5], "door_width": 1.3 }
```

It is **generated by `build_world.py` alongside the physics world**, and it is **read-only at
runtime**: nothing in `mak_demo/` writes to it. The camera never contributes to it.

This is a deliberate engineering choice with a precise justification: the robot has a single
monocular RGB camera (320 × 240, no depth channel) and the world is painted in flat colours with
almost no texture. Detecting an object is possible; *localising* it in map coordinates is not,
because a monocular image provides no scale and no range. A perception-built semantic map would
therefore have been fabricated, not measured.

The trade it buys: object coordinates are exact to the millimetre, identical to the simulator's
own placement table, so every navigation failure is a *real* failure rather than a data error.
The trade it costs: the map cannot be discovered, only authored — a new environment means
regenerating it, and moved furniture is invisible until the vision check at query time.

## 11.2 The lexicon, and how a phrase becomes a candidate

`mak_demo/data/lexicon.json` (35 entries) maps Chinese and English aliases to class names:
*fridge / 冰箱 / 雪柜*, *shoe cabinet / 鞋柜*, and so on. Resolution (`semantic_map.resolve_object`)
returns **scored candidates with reasons**, not a single answer:

```
"带我去那个放饮料的柜子"  → fridge_1  0.86  (alias 冰箱 + room context kitchen)
                          → wardrobe_1 0.31  (alias 柜子, wrong room)
```

Returning several candidates is what lets the LLM disambiguate with the user's own words, and
what lets the code refuse cleanly when nothing scores above threshold
(「家里没有叫「别了」的地方」 is the *wrong* behaviour of this mechanism, fixed in Chapter 12).

## 11.3 Standoff: where a robot should stand to interact with a thing

Object coordinates are centres; driving to a centre means driving into the object. The
`standoff_pose()` computation is pure geometry — 16 directions sampled around the object, each
candidate checked against the occupancy map, scored by clearance and by preference for facing the
room centre:

```
CLEAR_M = 0.45 m   # must equal Nav2 inflation_radius — 0.30 m looked clean but produced
                   # "map says passable, physics says stuck" pockets between fridge and chairs
GAP_M   = 0.55 m   # standoff distance = object radius + 0.55 m
```

When no candidate satisfies the strict thresholds, the search relaxes in stages
(`[0.45, 0.35] → [0.40, 0.25] → [0.32, 0.15]`), and the relaxation is recorded, because a
relaxed standoff is a warning that the object is in a tight place — precisely the situation that
produced the "irreversible squeeze" bug in phase 2A.

Two special cases:

* **Corridor landmarks.** Sixteen objects stand in the corridor but carry a room label
  (Chapter 3 §3.4). `standoff_pose` uses the physical position; only the label is topological.
* **Objects with no free neighbour at all.** The resolver reports failure rather than returning a
  pose inside furniture; the agent then answers "I can't reach it from here" instead of driving.

## 11.4 The observation pose, and why 0.55 m fails

Seeing an object is a different problem from standing next to it. The observation pose is:

```
distance = object radius + 1.40 m        (fridge: 0.39 + 1.40 = 1.79 m from centre)
camera height = 0.70 m                   (measured, not assumed)
```

This pair was established by an A/B experiment with exactly one variable — camera height — and
then by moving the *distance*, which turned out to matter more:

| Camera height | Standoff 0.55 m (side of object) | Observation 1.40 m (frontal) |
|---|---|---|
| 0.30 m | cannot identify objects; sees table legs and shelves | — |
| 0.70 m | sees the *side panel*: VLM calls the fridge a **door** | **correct**: fridge recognised |

The failure at 0.55 m is not a model problem. At that distance and a 1.204 rad horizontal field
of view, the object fills the frame with one flat side; a front-facing model has nothing to
recognise. The fix is geometric: back off and look at the front.

## 11.5 Mode D: vision confirmation with closed options

The VLM prompt is deliberately impoverished: a **closed list of all 28 object classes** plus a
short answer format, and one question per frame. Open-ended prompting produced confabulation —
an 8B model described kitchen floor tiles as bedsheets and called the fridge a door.

```
You see one photo from the robot's camera. Candidate classes: [28 names].
Answer in exactly this form: "The object is <class>." or "I cannot tell."
Do not describe the scene. Do not guess.
```

Measured: **13.1 s** warm (first call after model load is much slower), four checks green —
the object was named, the frame exists on disk (`logs/look_*.png`), the distance matched the
plan, and no other class was claimed.

Mode D is the *only* place the camera influences a decision, and even there its influence is
limited to a yes/no about identity. It cannot move the robot, and it cannot write the map.

## 11.6 Mode E: passability, where the camera is genuinely useful

A 2D laser slice answers "is there a gap at 0.78 m?" but not "can this robot get through?" —
an object below the slice, or a gap that is visible but too narrow for a 0.42 m body, both need
context. Mode E therefore combines:

1. **Laser sector analysis**: nearest return in the forward sector, and whether a free corridor
   of at least the robot's width exists; reported as a *tier* ("blocked", "can advance 0.91 m",
   "clear").
2. **Vision second opinion**: if the laser says "can advance", ask the VLM whether the way looks
   physically blocked (a fridge filling the frame, a chair lying across the aisle).
3. **Disagreement is reported, not averaged.** A verdict of "laser says 1.12 m, vision says
   blocked" is more useful to a human than a weighted score.

The module also carries a scar: `MIN_R = 0.12 m`. When the lidar was mounted such that it saw
its own mast (echoes at 0.124–0.138 m), that threshold passed them through and turned an open
corridor into "obstacle at the nose" (Chapter 4 §4.4d).

## 11.7 What the semantic map does not do

* It does not learn. Adding a room means regenerating from `build_world.py`.
* It does not detect a moved object. Mode D does, but only for the object you asked about.
* It does not know about anything that is not in the table (a box left in the corridor is only an
  obstacle, never a *thing*).
* Its labels are ownership labels, so a "in room X" query and a geometric point-in-polygon test
  will disagree for the sixteen corridor landmarks — by design.

> **Takeaways.** The semantic layer is authored truth, read-only at runtime, with millimetre
> coordinates and no perception. The lexicon returns scored candidates so ambiguity can be
> resolved rather than guessed. Standing next to an object and *seeing* it are different
> geometric problems (0.55 m vs 1.79 m). The camera's only job in the pipeline is identity
> confirmation and a passability second opinion.
