## 1. 相机链路实测（决定能不能用、怎么用）

| 项 | 实测值 | 说明 |
|---|---|---|
| 原生帧率 | **7.1 Hz** | 配置 10 Hz，RTF 打折后的真实值 |
| 分辨率 / 编码 | **320×240 rgb8**，step 960 | 无行填充 |
| 单帧像素 | **225.0 KB** | 320×240×3 = 230400 字节，尺寸吻合、无截断 |
| rosbridge 线路表示 | **base64 字符串 300.0 KB/帧** | `uint8[]` 经 JSON 自动转 base64（×1.33） |
| 实测带宽 | **2.36 MB/s**（8.04 fps） | 10 Hz 满速需 2.93 MB/s |
| **转 PNG 后** | **56~60 KB** | 比 raw base64 小 **5 倍** → VLM 输入一律用 PNG |
| VLM 单次延迟 | **10.1~25.9 s**（短回答）/ 41 s（自由发挥） | 本地 qwen3-vl:8b |

判读：
- **数据能过来，但不能当下行流用**。2.36 MB/s 持续跑会与导航抢带宽、agent 侧空转解 base64。
  正确用法是**按需抓单帧**（一次 ~300 KB raw，转 PNG 后 58 KB 送入模型）。
- VLM 延迟进不了控制环，但作为"到点后的一步确认"完全够用。

测量脚本：`dev/check_camera.py`（抓帧 + 统计 + 存 PNG）、`dev/check_vlm.py`（抓帧 + 问模型）。

## 2. 取景几何：为什么"贴到旁边拍一张"认不出物体

原来的相机位姿 `camera_link z = 0.104` + 传感器 `z = 0.013` → **离地 0.117 m**，
HFOV 1.204 rad（69°），320×240 → VFOV 54.5°。

冰箱（`build_world.py: fridge()`）真实的视觉特征是：
面板 0.78×1.80 m，**下把手 z=0.75、门缝 z=1.15、上把手 z=1.45**。

在 0.94 m 站位（镜头离柜面 0.55 m）时可见范围只有 **0.76 × 0.57 m，高度带 [-0.17, +0.40] m** ——
**三个判别特征全部在画面之外**，只框到一块无特征的柜面下部。像素上"冰箱"与"一扇门"等价。

`dev/check_framing.py` 输出的距离矩阵（相机 0.117 m）：

```
到点站姿 0.94 m（离柜面 0.55）   0.76×0.57 m   可见带 [-0.17, +0.40]   特征 0/3
退到 1.5 m（离柜面 1.11）        1.53×1.14 m   可见带 [-0.45, +0.69]   特征 0/3
退到 1.8 m（离柜面 1.41）        1.94×1.45 m   可见带 [-0.61, +0.84]   特征 1/3（下手柄）
退到 2.5 m（离柜面 2.11）        2.90×2.17 m   可见带 [-0.97, +1.20]   特征 2/3
```

`dev/check_camera_height.py` 的相机高度 × 观察距离矩阵（节选）：

```
相机高 \ 离柜面      0.55 m        1.00 m        1.41 m        2.11 m
0.117 m            0/3           0/3           1/3           2/3
0.300 m            0/3           1/3           1/3           2/3
0.450 m            0/3           1/3           2/3  ✅       3/3
0.600 m            1/3           1/3           2/3  ✅       3/3
0.800 m            1/3           2/3           3/3           3/3

选择 **0.60 m + 离柜面 1.40 m（约 1.8 m 距中心）**：比 0.45 m 更像真实机器的传感器立杆，
且只需改传感器位姿 —— 雷达、碰撞体、地图全不动。

## 3. 对照实验：只改相机高度一个变量

同一句开放式提问、同一个模型（qwen3-vl:8b）、同一台冰箱：

| 相机高度 | 观察距离 | VLM 回答 | 结论 |
|---|---|---|---|
| 0.117 m | 1.61 m | "可以推测是冰箱……带垂直长条的结构" | 猜对但没把握 |
| 0.117 m | 2.31 m | **"不能判断……底部浅色纹理表面（推测为床铺）……更符合卧室"** | ❌ 编造整个场景 |
| 0.117 m | 1.61 / 2.31 m（封闭式四选一） | **"答案=房门"**（两帧一致） | ❌ 与"门"不可分 |
| **0.60 m** | **1.79 m** | **"能判断它是一台冰箱 —— 立式长方体 + 右侧垂直长条把手 + 顶部水平横杠"** | ✅ 正确且依据真实 |

自己复核画面（不是信模型的描述）：抬高后那一帧确实有 **1 条清晰横缝 + 竖直长条把手 + 左侧悬空木柜 + 下沿地面**；

尺寸 320×240 一致、`frame_id` 相同、`K[0]=232.9` 反推 FOV **69.0° = HFOV 1.204** 完全吻合，
说明链路本身没有问题，问题全在几何与提问方式。

## 5. 提问方式：封闭选项 + 限长（和相机高度同等重要）

`vision.py` 的三条规则（都是被实测逼出来的）：

1. **封闭选项**：候选词来自语义地图的**全部类别**（33 类 + 「看不出」= 34 个），
   要求输出严格一行 `答案=<选项>；依据=<不超过15字>`；
2. **限长**：`num_predict=90`。开放式"描述画面里有哪些物体"会让 8B 模型开始写作文，
   耗时从 2.5 s 涨到 20~41 s，并出现上面"床铺/卧室"那种编造；
3. **只做确认，不做理解**：它回答的是地图不知道的事（物体还在不在、门开没开、通道是否被挡）。

### 5.1 选项集必须覆盖到被确认的类别（第一版是个真缺陷）

第一版写死了 10 个固定选项（冰箱/橱柜/门/墙/床/沙发/桌椅/垃圾桶/书架/看不出）。
核对后发现它只覆盖 **5/33** 个类别 —— 椅子、餐桌、床头柜、马桶、洗手盆、衣柜、电视柜、
绿植、盆栽、鞋柜等 **28 类全在选项之外**。后果很硬：用户说"看看椅子"时，
期望类别「椅子」不在候选里，模型只能从错的词里挑一个 → **必然被判"视觉与地图不符"**。
这是假告警，而且会把"物体被挪走 / 标注错了"这种真信号淹掉。

改成 `vision.full_options(expected)`：从语义地图现取全部类别 + 「看不出」，
并保证 `expected` 一定在内（不在就补进去）。`dev/check_vision_options.py` 验收 33/33 覆盖。

同一帧（冰箱）实测，选项集变大不影响准确率，反而更快：

| 选项集 | 耗时 | 答案 |
|---|---|---|
| 10 个（旧） | 10.8 s | 冰箱 ✅ |
| **34 个（全类别）** | **2.2 s** | 冰箱 ✅（依据：高大带门把手分上下） |

（推测：候选里挤着一堆近义干扰项（橱柜/墙/门）反而诱发更多思考。）
无论机制如何，结论是**没有理由用小子集**。

`vision.verify_object(expected)` 把答案与语义地图的正名比对，返回 `match = True/False/None`，
`None` 表示模型答"看不出"——既不算对也不算错，由调用方决定怎么处理。

## 6. 工具与意图：`look_at` 与模式 D

`tools.py` 新增第 6 个工具：

```
look_at(object_id)
  → 用 object_id 查物体 → observation_pose() → 开车 → 抓帧 → VLM → 与预期比对
  → 返回一行结构化结果："✅ 已到 X 的观察站位，距中心 1.79 m，耗时 …；视觉确认一致 ✅…"
```

`agent_nav.py` 新增模式 D（在原有 A/B/C 之外）：

```
ACT + "看看 / 看一眼 / 还在吗 / 确认" + 能解析到物体 → look_at
ACT + 其他 + 能解析到物体                          → go_to（贴到旁边）
ASK                                               → 带工具 LLM 查证
ACT + 解析不到                                     → 纯代码拒绝
```

`classify_intent()` 的顺序被修过一次（离线测试抓到的真实 bug）：
**先判"问位置"（在哪/哪里/有哪些），再判"要动手/要看"**。否则 `冰箱还在吗` 会掉进 ASK，
车不动只回一句"在厨房"——而用户问的是"还在吗"，就是要它去看一眼。

`dev/check_look_route.py` 9/9 通过：

## 8. 踩过的坑

| 坑 | 现象 | 根因 | 修法 |
|---|---|---|---|
| RViz Camera 报错 | `Status: Error` / `Error subscribing: Empty topic name` / `No CameraInfo received on [/camera_info]` | rviz 配置里写成 `Image Topic:`，**RViz2 的属性名是 `Topic`**，未知键被 YAML 静默忽略 → 话题留空 → camera_info 被推导成 `/camera_info` | 配置改成 `Topic:`；也可在运行中的 RViz 里直接填 `/camera/image_raw` 即时生效 |
| `tf2_echo base_link camera_link` 超时 | 只打印 Waiting，最后被杀 | TF 里根本没有 `camera_link`（URDF 用的是 `camera_rgb_frame`，且 z=0.107 是旧值） | launch 里补静态 TF `base_link → camera_link` (0.064,-0.065,0.590) |
| 图像 frame 名与 TF 名不一致 | 图像 `frame_id=camera_rgb_frame`，TF 里查不到对应 link | SDF 的 `<gz_frame_id>` 与 link 名不同 | `<gz_frame_id>` 改为 `camera_link` |
| 开放式提问引发编造 | 同一帧被描述成"床铺 + 卧室" | 8B 模型在开放式描述下补全场景 | 封闭四选一 + `num_predict=90` |
| 弱验收 | "到点"耗时 0.1 s 也判通过 | 车本来就在站位 | 验收必须包含一段真实行驶（≥10 m） |
| 核查行看不到 | 用户跑 `main.py` 时没有核查①~④ | 核查逻辑只写在 `agent_nav.main()` | 抽成 `agent_nav.print_checks()`，两个入口共用；`dev/check_checks.py` 5 种结局离线验证 |
| 雷达把车壳当障碍 | 出生点判"贴着车头有障碍、过不去"（0.13 m @ -25°） | `MIN_R=0.12` 放行了 0.124 的车体自遮挡回波 | 按车体矩形几何剔除（`|x|≤0.173, |y|≤0.1605`），输出 `self_rejected` 计数 |
| VLM 返回空回答 | `答案「空」`、18.1 s 白等 | qwen3-vl 是 thinking 模型，`num_predict=80` 全被思考吃掉（`done=length`） | 预算提到 600 + 截断重试 + 从 thinking 末尾捞答案；`dev/check_vlm_guard.py` 3/3 |
| `/no_think` 与 `think:false` | 以为能关掉思考，实测无效 | 这版 ollama 不认（思考照样输出，content 仍空） | 别再试这两条；靠预算 + 兜底 |
| 拿窗口截图当证据 | 我从 RViz 截图断言"正前方 0.2 m 有灰柱"，实际是空旷地面 | 低分辨率窗口截图 + 带倾向的提问 | 断言前的真值只看**存下来的原始帧**或传感器数据 |

一条通用教训：**"RViz 报错"不等于链路坏了**。先用脚本把 Image / CameraInfo / TF 三者测通，
再核对配置键名；校验脚本本身写错（我先前的 `check_rviz_cfg.py` 也只认 `Image Topic`）会掩盖真问题。

### 8.1 分辨率取舍：为什么最终维持 320×240

`model.sdf` 里的注释原本写着"要做视觉（VLM/VLA）时再调回 640×480@15"，但这次**没有调**：

- 相机每出一帧就是一次完整离屏渲染，而本机 RTF 已经只有 **0.34~0.58**，翻 4 倍像素会继续压低仿真速度，
  直接代价是导航变慢（阶段 2A 的实绩都是在这个 RTF 下取得的）；
- 抬高到 0.60 m 之后，320×240 已经能稳定认出冰箱（4/4 帧全部正确，VLM 10.1~11.7 s），
  **分辨率不是当前的瓶颈**；
- 真要提分辨率，优先降帧率：`640×480 @ 5 Hz`（像素 ×4、帧数 ÷2 → 渲染成本 ×2），
  而且我们只用"按需抓单帧"，不需要连续 15 Hz。

触发上调的条件应该是具体的：需要读标签/文字、需要识别小物体（垃圾桶、灭火器）、
或者观察站位距离被迫拉远导致目标像素数不足。到那时再量一次取景矩阵与 RTF，不要凭"更清晰更好"直接改。

## 11. 已知限制与下一步

**限制（都是当前设计的边界，不是 bug）**

| 限制 | 说明 | 后果 |
|---|---|---|
| 单帧单次判断 | 一次抓一帧、问一次，没有多帧投票 | 偶发误判无法自纠；`match` 只有对/错/看不出 三态 |
| 只从正面看 | 观察站位由环形采样选一个点，不环绕 | 侧面特征更明显的物体（如沙发靠背）可能认不出 |
| 依赖 lexicon 正名 | 选项与比对都用 `class_zh()` 的中文正名 | 用户口语（"电冰箱"）不影响比对（比对用正名），但地图标注写错就一路错 |
| 距离随物体尺寸变化 | 观察站位 = 半径 + 1.40 m | 沙发这类大件要到 2.65 m 外，目标像素更少 |
| 320×240 | 见 §8.1 | 小物体（垃圾桶、灭火器）可能分不清 |
| 无时序一致性 | 只用一帧，不比较连续帧 | 判断不了"正在移动"/"刚被放进来" |

**下一步可选（按价值排序）**

1. ~~把视觉用在它真正擅长的地方：可通行性问答~~ → **已实现，见 §12**。
2. **两帧一致才算通过**：同一站位抓 2 帧（间隔 0.5 s）分别问，两次答案相同才判 `match`，
   否则判"无结论"。成本翻倍（+2 s），但去掉偶发误判。
3. **失败可解释**：`match=False` 时把依据（`evidence`）和帧路径一起返回给用户，
   区分"我看到的是别的东西"与"我看不清"。
4. 需要更细细节时再上 `640×480 @ 5 Hz`（见 §8.1），并同步复测 RTF 与取景矩阵。

## 12. 可通行性问答（相机真正擅长的活）

物体身份识别在这台机器上受取景几何限制（§2/§3），但"正前方这条路现在能不能过去"恰好落在
两路传感器的互补区间里：

| 传感器 | 强项 | 盲区 |
|---|---|---|
| 2D 雷达（0.132 m 平面） | 墙、家具的几何真值，毫秒级 | **贴地线缆、门槛、地毯边、透明玻璃**（不在该平面上） |
| 相机（0.60 m，正前） | 地面细节、门缝/开合、透明与扁平物 | 深度不准、单帧无时序 |

所以不做"二选一"，而是**双源对照 + 明确谁说了算**：雷达给几何硬约束，视觉补雷达看不见的东西，
不一致时以雷达为准但如实报出视觉的怀疑。

### 12.1 雷达量测（`passability.py`，纯函数 + 一个订阅）

```
扇区    正前方 ±25°（约等于车宽在 0.5 m 处张开的角）
过滤    NaN / Inf / 0 / > 3.0 m；**车体自遮挡用几何判断**（见下）
输出    min_dist、min_angle、beams、self_rejected、free_until = min_dist − 0.21（车体半径）
```

**车体自遮挡必须按几何剔除，不能靠最小距离阈值。** 实测踩过：车在出生点 (0,0,0) 时，
雷达有 10 个回波落在 **0.124~0.138 m、角度 -24°~-31°**，换算到车体系是 `(0.054, -0.055)`
—— 完全在车身内（雷达 `base_scan` 装在 `base_link` 前方 **-0.064 m** 处，车体 0.306×0.281，
所以车壳会伸到雷达前方 0.089 m）。当时用的 `MIN_R = 0.12` 刚好放行 0.124，
于是"开阔走廊"被判成"贴着车头有障碍 → 过不去"。

现在的做法：把回波点换算到 `base_link` 系，落在车体矩形（`|x| ≤ 0.153 + 0.02`、
`|y| ≤ 0.1405 + 0.02`）内就丢弃，并在输出里带上 `self_rejected` 计数。
这样既不会误吃自身回波，也不会把**真实**的近障碍（一定在车体外）一起过滤掉 ——
`MIN_R` 因此可以放宽到 0.05。

判据（**四档**，不是三档）：

| free_until | verdict | 说法 |
|---|---|---|
| ≤ 0.15 m | `blocked` | 过不去，几乎贴着车头 |
| ≤ 0.60 m | `tight` | 勉强能过、风险高 |
| ≤ 1.50 m | `partial` | **能走一段，但前方不是畅通通道** |
| > 1.50 m | `open` | 前方畅通 |
| 3 m 内无有效回波 | `no_return` | 前方空旷（等同 open） |

为什么加 `partial`：第一版只有三档，1.5 m 外有墙会判"可以通过" —— 对"能不能过去"是误导，
因为车能走 1.29 m 然后就撞上。`partial` 把"能走一小段"和"是通道"区分开，实跑里冰箱在 1.4 m 处
正落这一档。

### 12.2 视觉问答（`vision.assess_passability`）

封闭三选一 + 限长，并明确把"地上的线缆/门槛/地毯边/透明玻璃"写进提示词，
同时排掉"地面有花纹"这种假阳性：

```
只回答：画面正中的前方通道，机器人能不能直接穿过去？
选项：畅通 / 被挡住 / 看不清
只输出一行：答案=<选项>；依据=<不超过15字…>
```

**token 预算必须按 thinking 模型给（600，不是 80）。** 实测同一帧、同一问题：

```
num_predict=80    2.1 s  done=length  content=''   thinking=135 字  ← 空回答（真机 bug）
num_predict=200   3.8 s  done=length  content=''   thinking=322 字  ← 仍然空
num_predict=600   6.1 s  done=stop    content=14 字 thinking=500 字 ← 「畅通」，正确
```

关思考的两条老办法**在这版 ollama 上都不生效**：`think: False`（思考内容照样输出）、
prompt 加 `/no_think`（仍 `done=length`、content 空）。所以 `vision.ask_vlm_detailed()`
做了三层防护：给足预算 → 检测到"截断且 content 空"就翻倍重试一次 →
仍空则从 thinking 末尾正则捞 `答案=`，并把 `truncated` 标记带回调用方
（`dev/check_vlm_guard.py` 3/3 覆盖：正常 / 重试成功 / 兜底捞回）。

顺便记录一个反面选项：`gemma3:12b` 没有 thinking（2.2 s、稳定出 19 字），
但在同一帧上把**两侧**的桌椅绿植当成挡路，答"被挡住"—— 而真值是"畅通"。
关思考省下的几秒不值得换来一个判断错误。

### 12.3 合并规则（`tools.check_path`）

| 雷达 | 视觉 | 结论 |
|---|---|---|
| blocked / tight | 任意 | 不建议通过（雷达硬约束）；视觉同报"被挡住"时注明"两者一致" |
| partial | 被挡住 | 能走一小段但前方有阻挡物，两者一致 |
| partial | 畅通 | 能走一小段；**视觉看着开着，但雷达的距离是硬约束** |
| open / no_return | 畅通 | ✅ 可以通过 —— 两者一致 |
| open / no_return | 被挡住 | ⚠️ 不一致：以雷达几何为准，但可能有雷达看不见的薄/扁/透明障碍，建议减速或换方向 |
| open / no_return | 看不清 | ✅ 前方畅通（视觉没给结论） |
| no_data | 任意 | 只有视觉可参考 |

工具返回三段结构化文本（雷达 / 视觉 / 结论），reporter 只负责把它说成人话，
不许自己加"遇到障碍物"之类的剧情。

### 12.4 意图：模式 E

```
ACT + "能过去 / 能过吗 / 通不通 / 挡住 / 有障碍 / 堵住 / 门开着 / 前面能…" → E：check_path（不开车）
```

放在 A/D 之前判断：这类指令既没有导航目标（会被误判成 C 拒绝），也不该让 LLM 凭地图回答 ——
地图是静态的，此刻有没有东西挡路只有传感器知道。

### 12.5 离线验收（`dev/check_passability.py`，19/19）

A 组用合成 LaserScan 覆盖 12 种扫描形态：

```
✅ 0.30 m 有墙 → blocked（free 0.09）
✅ 0.60 m 有墙 → tight（free 0.39）
✅ 1.50 m 有墙 → partial（free 1.29）
✅ 8 m 外才有墙 → no_return（3 m 内无回波）
✅ 障碍只在左侧 40°（不在扇区）→ no_return
✅ 贴车身 0.05 m 回波（自身遮挡）→ 被忽略（self_rejected=20）
✅ NaN/null 混入 → 仍正确取到 1.50 m
✅ 【回归】只有车体自遮挡回波（0.13 m @ -25°）→ no_return（真机 bug 前会误判 blocked）
✅ 【回归】真实障碍在车体外的 0.30 m 正前方 → blocked
✅ 【回归】真实障碍 0.40 m 偏右 20°（车体外）→ tight
✅ 全 inf → no_return
✅ 空消息 → no_data
```

B 组路由 7/7：`前面能过去吗 / 这条路通不通 / 有东西挡着吗 / 门开着吗` → 模式 E；
`去冰箱旁边` 仍走 A；`冰箱还在吗` 仍走 D；`洗手间在哪` 仍走 ASK。

`dev/check_vlm_guard.py` 3/3：正常返回一次成功 / 截断后重试成功 / 两次截断后从 thinking 兜底捞回。

`dev/check_checks.py` 增加一条"可通行性核对"结局，核查③会打出结论行而不是"已到达"。

### 12.6 实跑提示

贴着冰箱站位（离柜面 0.55 m）      → tight（free 0.34）→ 勉强能过、风险高
```

## 13. 车体结构改造：传感器塔（2026-10-23）

### 13.1 问题：那根"幽灵杆"插进了雷达扫描平面

为了让相机到 0.60 m，先前的做法是在 `camera_link` 下挂一根 `radius=0.012`、**只有 visual、
没有 collision** 的立杆。它的几何是这样：

```
立杆 span        z = 0.13 ~ 0.60 m      ← 底端正好在雷达 0.132 m 平面上
立杆中心         (x=0.064, y=-0.065)    radius 0.012
雷达位置         (x=-0.064, y=0)        装在车体中心偏后
实测自身回波     0.124 ~ 0.138 m @ -24°~-31°   → 换算到车体系 (0.054, -0.055)
```

`(0.054, -0.055)` 就在立杆边缘（杆的最近点在 `(0.052, -0.053)`），差不到 2 mm。
**"雷达扫到自己"的元凶是这根杆，不是车壳**。当时用 `MIN_R = 0.12` 过滤，
0.124 刚好漏过去，于是"开阔走廊"被判成"贴着车头有障碍 → 过不去"。

### 13.2 为什么必须先改结构，而不是继续加过滤

一条自洽性论证：**任何从车体升到 0.6 m 的支撑，都必然穿过 0.132 m 的平面**。
所以"低雷达 + 高相机"这个组合在机械上不成立 —— 要么雷达升高让支撑落在它下面，
要么永远得靠软件去擦掉自身的回波。软件过滤治的是症状（而且第一次就漏了），
结构改造才是根因修复。

### 13.3 新结构（`models/lighthouse/model.sdf`）

```
            相机 0.70 m ●  ← 挂在塔身前侧，低于雷达
                        │
   雷达 0.78 m ═════════╪════  ← 塔顶座 r=0.040（0.72~0.78）
                        │
                        █ 塔身 cylinder r=0.055，0.10（底盘顶面）→ 0.72
                        │   有 <collision>，是真结构，不是幽灵杆
                 ┌──────┴──────┐
                 │   TB3 底盘   │
                 └─────────────┘
```

| 部件 | 几何 | 说明 |
|---|---|---|
| 塔身 | 圆柱 r=0.055，z=0.10→0.72 | visual + collision，挂在 `base_link` 上（共享底盘惯量，不新增 link → TF/动力学/Nav2 footprint 全不变） |
| 雷达座 | 圆柱 r=0.040，z=0.72→0.78 | 同上 |
| 相机支架 | box 0.058×0.050×0.040 @ x=-0.036, z=0.70 | 从塔面伸到相机 |
| `base_scan` | (-0.064, 0, **0.78**) | 雷达本体 + gpu_lidar，360° 平面上无任何车体部件 |
| `camera_link` | (-0.004, 0, **0.70**) | 相机本体无 collision |
| ~~`mast_visual`~~ | 已删除 | 幽灵杆 |

**为什么 360° 干净**：0.78 m 平面上只剩塔顶座（r=0.040）和相机支架尖端，
它们离雷达轴都 < 0.06 m，而 LDS-01 的 `range_min = 0.12 m` —— 落在死区里，看不见。

### 13.3.1 TF 必须跟着改：自己维护一份 URDF

踩过的坑，值得单独记：**SDF 的 `<pose>` 只影响 Gazebo 的物理/渲染位置，ROS 的 TF 树完全来自
`robot_state_publisher` 加载的 URDF**。改完 SDF 后 `tf2_echo base_link base_scan` 依然报
`z=0.122` —— 因为官方 URDF 里 `scan_joint` 就写死在 0.122。

更糟的是，官方 waffle URDF 里**本来就有 `camera_link`（0.064,-0.065,0.094）**，
之前那条 `base_link→camera_link` 静态 TF 其实一直在和 `robot_state_publisher`
抢同一个帧 —— `tf2_echo` 会交替打印两个不同的值（0.094 / 0.590）。

正确做法（已实施）：**复制一份官方 URDF 到 `models/lighthouse/robot.urdf`**（改名 Lighthouse），
改两处几何，并补上塔身的 visual（顺带 RViz 里也能看到塔了）：

| URDF 元素 | 改造前 | 改造后 |
|---|---|---|
| `scan_joint` origin | `-0.064 0 0.122` | **`-0.064 0 0.770`** |
| `camera_joint` origin | `0.064 -0.065 0.094` | **`-0.004 0 0.690`** |
| `tower_joint` + `tower_link` | 无 | 新增：塔身 r=0.055 l=0.620 @ z=0.400；雷达座 r=0.040 l=0.060 @ z=0.740（仅 visual） |
| launch 里的相机静态 TF | 有 | **已删除**（否则两发布者抢帧） |

`LH_URDF` 指向 `HERE/models/lighthouse/robot.urdf`（`LH_MODEL` 同时作为 `mesh_dir:=` 传给 xacro）；
`xacro` + `check_urdf` 均能正常解析（266 行）。

### 13.8 更名：TurtleBot3 → Lighthouse（灯塔）

改完塔身之后，这台车已经不满足"TurtleBot3"这个名字的任何一个前提（雷达高度、
相机高度、URDF、外形都变了），继续叫 TB3 只会误导后来看代码的人。所以做了更名，
原则是**结构照抄官方思维，该改的大胆改**：

| 项 | 改造前 | 现在 |
|---|---|---|
| 模型名 | `turtlebot3_waffle` | **`lighthouse`** |
| 目录 | `models/turtlebot3_waffle/` | **`models/lighthouse/`** |
| URDF `<robot name>` | `turtlebot3_waffle` | **`lighthouse`** |
| 视觉网格 | `package://turtlebot3_description/...`（系统路径） | **`models/lighthouse/meshes/`**（复制进项目） |
| SDF 网格 | `file:///opt/ros/humble/share/...` | **`model://lighthouse/meshes/...`**（靠 launch 里设的 `GZ_SIM_RESOURCE_PATH`） |
| URDF 网格 | 同上 | **`$(arg mesh_dir)/meshes/...`**（launch 传绝对路径） |
| world 里的 `<include><name>` | `tb3` | **`lighthouse`** |
| launch 变量 | `TB3_URDF` | **`LH_URDF` / `LH_MODEL`** |
| RViz 里 | 官方 TB3 外形 | 塔身可见 |

**保持不变**（这些是 ROS 约定，不是身份）：frame 名 `base_footprint / base_link /
base_scan / camera_link / imu_link / wheel_*`，以及 joint 名、话题名、Nav2 参数。

保留"血缘"说明：`model.sdf`、`robot.urdf`、`launch` 三处文件头都写明了
"底盘/轮子/IMU 参数沿用官方 turtlebot3_waffle.urdf"，方便追溯与对照学习。
